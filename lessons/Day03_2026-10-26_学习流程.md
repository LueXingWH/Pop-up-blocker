### 必要原理：句柄、对象身份与生命周期

HWND 是窗口句柄类型，供符合契约的窗口 API 引用窗口；HANDLE 是 Windows 中多种资源接口采用的一般句柄类型名称。它们在原生声明中可能用到指针形态的底层类型，但对调用者而言句柄是**不透明标识**，不是可自行解引用的目标内存地址。Python 包装以整数表示 HWND，不因此允许你推算其结构、做地址运算或把任意整数当有效窗口。

指针表达内存地址，是否可以读取还受地址空间、类型、访问权限和有效期约束。即使知道另一个进程的窗口句柄，也没有因此获得读取其任意内存的能力。不同句柄类型必须使用各自 API，不能把“释放 HANDLE”的经验套成对别人的 HWND 调 `CloseHandle`。

窗口销毁后句柄会失效，数值也可能复用；保存整数不会延长对象生命周期。今天核对的是当次目标，不把历史句柄写进配置长期使用。这些区别用于后续识别模块与关闭模块的输入契约。[Windows 数据类型](https://learn.microsoft.com/en-us/windows/win32/winprog/windows-data-types)、[用户对象及其管理 API](https://learn.microsoft.com/en-us/windows/win32/sysinfo/user-objects)

## 3. 任务二：给确认过的单个目标投递一次正常请求

### 消息、投递和实际结果

窗口不是一个可以直接“删掉”的 Python 对象。你的程序与目标程序属于各自的进程；Windows 为窗口提供消息处理机制。`WM_CLOSE` 是系统约定的一类消息，目标收到后有机会决定如何响应。处理它的程序可以先询问是否保存，再决定销毁窗口；不能由发送端保证一定出现提示或一定关闭。[Microsoft：WM_CLOSE](https://learn.microsoft.com/en-us/windows/win32/winmsg/wm-close)

`PostMessage` 的工作像投递通知：本次调用成功表示投递环节成功，不表示收件人已处理。目标忙碌、忽略消息或等待用户选择时，窗口都可能还在。因此实验记录至少分开写“调用是否报错”和“我看到什么”。[Microsoft：PostMessage](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-postmessagew)

这里选异步投递，是为了发起正常请求时不等待目标处理结束。同步 `SendMessage` 会等待目标窗口过程处理，可能带来等待问题；本课无需实现或比较所有替代方案，不声称它在所有场景都更差。

关闭窗口与结束进程也不同：同一进程可能有多个窗口，程序还可能常驻后台。本课不调用结束进程、强制销毁其他程序窗口的接口，也不在请求失败时升级为强杀。目标程序自己如何处理未保存内容，是观察与记录对象。

另外，`win32gui.CloseWindow` 的名字容易误导：Windows 的这个 API 用于最小化窗口，并不是这里要学习的正常关闭请求。[Microsoft：CloseWindow](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-closewindow)

| 当前需要与使用位置 | 当前方案及理由 | 替代方案与权衡 |

### 本任务所需函数、常量与返回契约

下面各行是独立调用形式，不是可复制的完整关窗流程。`hwnd` 等名称表示你要传入的数据；先核对输入含义，再使用自己的变量。

| 调用形式 | 参数、返回与边界 | 本任务用途与时机 |
|---|---|---|
| `win32gui.PostMessage(hwnd, message, wparam, lparam)` | `hwnd` 为目标句柄；`message` 为消息编号；后两项含义由消息定义。本包装成功返回 `None`，失败抛出 Windows 异常 | 仅在确认当前测试目标后投递一次。它不返回目标是否已经关闭 |
| `win32con.WM_CLOSE` | 命名常量，值为 `0x0010` / `16`，无时间或像素单位 | 作为上行的消息编号；不是等待时长，不随意改数字 |

`WM_CLOSE` 的 `wParam`、`lParam` 均未使用，本课二者传 `0`。这两个零来自该消息契约；不能推广为“所有 Windows 消息都传零”。与句柄位置传 `0` 完全是两回事。

**句柄参数不可用 `0`、`None`、广播常量或旧记录中的数值代替。** 原生 `PostMessage` 对空句柄和广播句柄有特殊含义，并非“什么都不做”；本课只对当次已确认的单个测试窗口实验。

尤其注意 Python 与 C 文档的差异：C 的 `PostMessageW` 返回 BOOL；pywin32 将这里的成功映射为 `None`、失败映射为异常。因此不能用“Python 返回值为假”判为失败，也不能把 `WM_CLOSE` 接收方的返回值当作发送函数的返回值。依据：[包装签名](https://mhammond.github.io/pywin32/win32gui__PostMessage_meth.html)、[维护者 BOOLAPI 转换定义](https://github.com/mhammond/pywin32/blob/main/SWIG/swig_lib/python/pywintypes.i)、[绑定声明](https://github.com/mhammond/pywin32/blob/main/win32/src/win32gui.i)。

权限边界：UIPI 会限制较低完整性级别向更高等级窗口投递消息，可能出现错误码 5。当前产品预期管理员启动，两种策略均核对实际提升状态；开发时由用户在已提升终端运行项目解释器。先用明确的普通测试目标，失败记录具体 API/权限与原文，不把管理员当作任意目标可操作的保证，不自动强杀。

### 异常机制、局部示例与实际使用

你已有基础语法，不重复练赋值、循环或元组。本节只针对 Windows 调用中的异常与收尾；若已熟悉语法，快速看异常类型的迁移即可。`try` 内出现匹配异常时跳到 `except`；`as` 给异常对象取本地名字；`finally` 在正常返回或异常退出时都用于收尾。它不能保证断电或强制终止进程时执行。

以下独立例子只用于不熟悉异常语法时理解控制流，已懂即可跳过，不安排为独立学习任务。开发时间优先留给本课请求与失败反馈：

```python
raw = "两杯"
try:
    cups = int(raw)
    print("杯数：", cups)
except ValueError as error:
    print("输入不是整数：", type(error).__name__)
finally:
    print("本次检查结束")
```

逐步看：`int` 无法把“两杯”转成整数，抛出 `ValueError`，所以“杯数”不打印；匹配的 `except` 显示异常类型，最后仍打印收尾文字。

预期输出：

```text
输入不是整数： ValueError
本次检查结束
```

若需排查自己的异常分支，可把 `raw` 改为 `"2"` 比较正常路径；理解后回到关窗文件处理真实 Windows 异常。无需另交练习或把示例加入项目。

在 Windows 实验中，异常类型用 `pywintypes.error`，不是上例的 `ValueError`。对这类异常，`error.winerror` 是错误码，`error.funcname` 是 API 名，`error.strerror` 是说明；完整打印异常也能保留关键信息。导师给的是异常工具用法，具体在哪捕获、如何终止本轮由你设计。不要用不分类型的捕获配合 `pass` 隐藏失败。[Python：异常](https://docs.python.org/zh-cn/3/tutorial/errors.html)

## 7. 常见错误与排查顺序

固定顺序：解释器与导入 → 本次目标与层级 → 确认是否有效 → 消息和参数 → 包装异常 → 目标的实际行为。

| 现象 | 优先核对 |
|---|---|
| 提示 `ModuleNotFoundError` | 是否用项目 `.venv`，安装名与导入模块名是否混淆 |
| 返回 `None`，日志却报失败 | pywin32 的成功返回约定；不要套用 C 的 BOOL 判断 |
| 日志说发送成功，窗口仍在 | 是否等待保存、软件自身策略或消息尚未处理；不要直接归因于接口失败 |
| 目标最小化了 | 是否误用了 `CloseWindow` |
| 错误 5 | 目标权限是否比本程序高；记录限制，先回同权限测试条件 |
| 无效句柄错误 | 目标是否已关闭/重建，是否使用旧数值或子窗口句柄 |
| 提示出现后连续弹出/重复请求 | 查本轮请求次数和重复调用来源，不用加长 sleep 掩盖 |
| 未保存测试没有提示 | 先比较该软件手动关闭时的行为；自动保存与会话恢复会改变观察 |

## 8. 技术面试与参考答案

题目与对应参考答案放在一起，可自主阅读、复述或按需分次复习，无需逐题回复。看过答案与能独立解释分别记录。

### 模块 A：句柄、对象身份与生命周期（3 题）

#### A1. HWND、一般 HANDLE、指针分别表达什么？为什么 pywin32 给出的整数不能当内存地址，也不能随意交给其他资源 API？

**参考答案**：HWND 按窗口接口契约引用窗口；HANDLE 是其他许多 Windows 接口使用的一般句柄类型；指针表达某地址空间里的内存位置。原生类型的表示方式不赋予调用者解引用句柄的权利。pywin32 的整数只是包装表示，不是窗口对象地址或永久身份。项目把 HWND 传给窗口 API；不能用 `CloseHandle` 释放别人的窗口，也不通过算术猜新句柄。易错点是把“底层可能用指针类型声明”理解为“可以读取指向的窗口结构”。

#### A2. 先 `IsWindow` 得到真，再发送请求，为什么仍可能失败甚至面对已改变的对象？延长等待或多查一次能彻底消除风险吗？

**参考答案**：`IsWindow` 只观察调用时刻；查询后目标可能销毁，句柄数值可能被复用。检查与投递不是跨进程原子事务。项目应缩短间隔、核对当次身份、信息改变就放弃，并处理真实投递错误；这些只降低风险，不承诺零竞态。多等待通常还会增加变化机会。追问“查三次是否保险”：仍有最后一次检查与使用之间的间隙，不能把次数当锁。

#### A3. 为什么对关闭目标要比较直接命中与根窗口？标题相同、类名相同、句柄在两次运行中相同，分别能证明什么？

**参考答案**：命中可能是子窗口，根窗口有助于定位这次实验想请求关闭的顶层对象，但 owner 对话框与父子层级还要区别；不能对所有特殊界面盲目套用。标题可重名/为空，类名可被同类窗口共用；它们是诊断属性。跨生命周期相同数字不能证明还是原对象。项目保留命中与根的信息供核对，查询失败停止本轮，不靠标题或数值巧合确认目标。

### 模块 B：消息机制、调用契约与权限（4 题）

#### B1. 比较 `WM_CLOSE`、`PostMessage`、`SendMessage` 和结束进程；本项目为何选择当前组合，有什么代价？

**参考答案**：`WM_CLOSE` 是意图，两个发送 API 是传递机制，进程终止则作用于整个进程，层次不同。`PostMessage` 入队后返回，适合普通模式发正常请求而不等待目标完成；代价是不能同步得知关闭结果。`SendMessage` 等窗口过程处理，返回依消息定义，也不是关闭成功证明。强制模式独立选择，可能影响同进程其他窗口及保存流程；不能当普通模式失败后备。两策略与退出确认见双模式契约。不要把异步投递误说成所有路径都永不耗时。[PostMessage](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-postmessagew)、[SendMessage](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendmessage)

#### B2. 分析请求的四个参数，以及消息编号 `16`、两个附加参数 `0`、等待 `3` 秒的来源。为什么句柄位置不能也随手填零？

**参考答案**：四项依次是目标 HWND、消息编号、消息定义的两个附加参数。`16` 是 `WM_CLOSE` 协议值，无时间单位；该消息两附加参数未使用，传零；`3` 秒是人为移动时间，可按体验调整。句柄零在原生接口有特殊语义，不代表安全空操作；广播也会扩大影响。本项目只使用本次确认的单个目标。易错点是将“这个消息未用附加参数”推广成“所有消息都一样”。

#### B3. 某代码把 `PostMessage` 的返回值按真/假判断成功，调用没有异常却报告失败。原因是什么？C 的 BOOL、Python 包装返回值、接收方的消息处理结果有什么区别？

**参考答案**：本包装成功返回 `None`，它是假值；失败通过 Windows 异常表达，所以真假判断会误报。C API 的 BOOL 表示投递是否成功，pywin32 已将它转换；目标处理 `WM_CLOSE` 的返回又属于接收方消息过程，本次异步投递拿不到它。项目记录“调用无异常，已提交请求”与观察结果两项，不能将 `None`、接收方返回零或目标还在混为一个失败条件。返回约定依据第 3 节的包装与转换定义。

#### B4. 软件预期管理员启动，为什么仍需记录实际权限与错误 5 的具体 API？普通模式失败能否自动强杀，应用 manifest 与安装器权限有什么区别？

**参考答案**：先区分产品预期与实际进程权限：管理员账户不等于已提升，安装器权限也不等于应用 manifest 已请求提升。软件预期管理员启动仍须实测 UAC 同意/取消、调试与安装后运行状态。错误 5 要结合具体 API、原文和目标判断；管理员不保证所有访问可用。普通策略失败只反馈，不自动改强制；需要强制应先退出会话、显式切换并重新开始。新策略尚未实测，不能把需求改动说成已修复权限 Bug。

### 模块 C：异常、结果验证与组件接口（3 题）

#### C1. 投递成功但窗口还在，至少有哪些原因？如何设计未保存内容实验，证明工具没有绕过目标自己的处理？

**参考答案**：目标可能尚未处理、忙碌、显示保存确认、忽略请求或按自身策略继续运行。先手动关闭建立基线，再用可丢弃内容测试请求与取消；若该编辑器默认自动恢复、无提示，不能据此验收“保留提示”。检查脚本只发一次、不自动点弹窗/重试/强杀。窗口消失也只说明观察到窗口不在，不能推断进程退出或所有数据都已保存。[WM_CLOSE](https://learn.microsoft.com/en-us/windows/win32/winmsg/wm-close)

#### C2. 异常处理应该保留什么？为什么 `except: pass` 和“最后一定打印关闭成功”都会破坏验证？`finally` 能保证什么、不能保证什么？

**参考答案**：保留出错 API、错误码、文本、当次目标和操作时序，必要时完整回溯；只有正常超时等明确条件才按其语义处理。吞异常会失去失败证据，无条件成功文字会误导后续 GUI。`finally` 适合释放自己拥有的资源与收尾，即使普通异常退出也会执行；它不能保证强杀/断电时运行，也不能证明目标完成关闭。修改后重测拒绝确认、目标消失及正常路径，而不只看无报错。

#### C3. 今天的组件将由界面哪里触发、向界面返回什么事实？怎么证明自己完成的是可接入 GUI 的能力，而不是把终端脚本当最终软件？

**参考答案**：未来先由“开始清理”建立模式，再由有效选择和过滤调用关闭组件，界面获得“未执行及原因 / 请求投递失败 / 已投递”等事实；“已观察到窗口消失”须另有观察证据。今天可以独立验收组件输入、一次请求与失败行为，但 GUI 事件接线、光标、构建和安装卸载仍是后续任务。不能把 `input()` 原样搬到 GUI 线程，或在按下开始时就关闭当前前台窗口；模块组织与接线由用户实现。
