## 2. 任务一（A 阶段）：创建监听，观察按下/松开并能停止

**必须独立编写的核心**：监听创建/收尾、事件分类、选择性拦截、点位复制、取消与配对、模式边界及业务通知。**AI 可辅助的非核心**：本次教程、接口资料、测试记录格式、文案建议与代码审查；需要 AI 修改辅助文件或制作 UI 时另按明确授权执行，不替你完成上述功能。

### 必要原理：事件、全局钩子与回调

**WH_MOUSE_LL 基础**：这是 Windows 低层鼠标钩子类型（协议常量值 14），与只在自己 QWidget 内接收鼠标事件不同。原生回调接收控制码 `nCode`、消息类型 `wParam`、指向鼠标事件结构的 `lParam`；需要在安装线程的消息调度机制下被及时处理。未消费的事件应按原生契约继续传递，回调过慢可能被系统移除，所以只做短操作并安排卸载/退出。本课通过封装验证机制，不要求先自行绑定 C 回调；pynput filter 的 `(msg, data)` 是另一层接口，不能照抄原生参数个数。依据：[LowLevelMouseProc](https://learn.microsoft.com/en-us/windows/win32/winmsg/lowlevelmouseproc)。

**事件回调**：你先把一个函数交给库，系统事件出现时库才调用它，并把事件信息作为参数传入。你的主线程不必不断读取当前鼠标位置。一次点击包含按下和松开两个事件；按住键盘键还可能产生重复按下。

**监听**：收到通知不等于拥有输入。只用普通点击回调识别，原点击仍可能让目标按钮执行、编辑区改变光标或任务栏切换窗口。选窗器需要把用于点选的那次输入消费掉。

### 本课技术选择与工程位置

| 当前需要与位置 | 当前方案及理由 | 替代方案与权衡 |
|---|---|---|

### 本任务所需函数：普通回调与生命周期

导入：`from pynput import mouse, keyboard`。以下变量名表示你自己定义的对象或函数，不是完整程序。

| 调用形式 | 参数、返回与边界 | 本任务用途与时机 |
|---|---|---|
| `mouse.Listener(on_click=click_handler, suppress=False)` | `click_handler` 是函数对象；构造返回 listener，尚未启动 | A 阶段观察点击；回调形如 `def click_handler(x, y, button, pressed):`，位置是当时屏幕点，`pressed` 表示按下或松开，`button` 与 `mouse.Button.left/right` 比较 |
| `keyboard.Listener(on_release=key_handler, suppress=False)` | 回调函数接收 `key`，返回 listener | A 阶段识别 `keyboard.Key.esc`，其他键不读取文字、不逐键输出；普通字符不一定有 `.name`，特殊键不一定有 `.char` |
| `listener.start()` | 无参数，正常返回 `None`；后台启动 | 主线程继续运行；不能主线程马上结束，否则监听实验随进程退出 |
| `listener.wait()` | 无参数，无需使用其返回值；等待库报告 ready | 主线程做启动等待；若启动异常或卡住，先回 A 阶段排查，不能把等待本身当作拦截成功 |
| `listener.stop()` | 无参数，正常返回 `None`；请求停止 | 正常配对收尾后或异常恢复时清理资源；不等于已经等待线程退出 |
| `listener.join(timeout=1.0)` | 可选超时以秒计；返回 `None`，回调异常可能在此重新抛出 | 在主线程收尾；不能从该 listener 自己的回调中等待自己 |
| `listener.is_alive()` | 无参数，返回布尔值 | 超时等待后核对线程是否仍在；不能因 join 返回就假定已退出 |

listener 停止后不能再次 `start()`；重复试验可新建实例，或后续设计常驻监听、仅切换业务模式。选哪种由你说明并实现。普通回调停止一个 listener 不会自动停止另一个。`wait`、`join` 均不放在未来 GUI 主线程里长期阻塞。[鼠标文档](https://pynput.readthedocs.io/en/latest/mouse.html)、[键盘生命周期](https://pynput.readthedocs.io/en/latest/keyboard.html#toggling-event-listening-for-the-keyboard-listener)、[启动等待定义](https://pynput.readthedocs.io/en/latest/_modules/pynput/_util.html)

## 3. 任务二：把必要事件传给主线程，并设置实验期限

**位置与目标**：继续自己的 `lessons/day04_pick_only.py`，回调只复制必要事件，主线程负责后续处理与结束检查，未来在这里建立 GUI 通知边界。A 阶段启动/停止已可靠时再做此任务。

### 本任务所需函数、参数与机制

导入 `import queue`、`import threading`、`import time`。本课不会要求你凭空发明线程通信 API。

| 调用形式 | 参数与返回 | 本课用途 |
|---|---|---|
| `queue.Queue()` | 无参创建 FIFO 队列；默认容量不设上限 | 回调向主线程传必要的小事件，不传大量移动事件 |
| `events.put_nowait(item)` | `item` 是自己的 Python 数据；正常返回 `None` | 回调短暂入队；若日后设置容量上限，会有 `queue.Full`，需要明确处理 |
| `events.get(timeout=0.1)` | 超时单位秒；返回并移除一个 item，超时抛 `queue.Empty` | 主线程等事件，约每次超时有机会检查退出条件；不在回调里等待 |
| `threading.Event()` | 创建内部初始为假的线程通知标志 | 表达某个单一条件，例如本轮正在接受选择；用途由你明确命名 |
| `flag.set()` / `flag.clear()` | 无参，分别置真/置假，返回 `None` | 发布单个标志变化；不自动停止监听或清空队列 |
| `flag.is_set()` | 无参，返回布尔值 | 查询单一条件；“先查询再修改多个状态”并非因此自动成为原子操作 |
| `time.monotonic()` | 无参，返回单调时钟浮点秒数；起点无业务意义 | 两次差值判断实验已用多久，不受墙上时钟校准影响 |

`0.1` 秒是主线程定期检查退出的教学选择，不是鼠标采样周期，不要求回调等待它。`15` 秒是实验上限；`join` 的 `1.0` 秒是等待线程收尾的检查窗口；三者作用不同。调大或调小要说明响应和等待的影响。

主线程在有事件与没有事件时都要检查总期限，不能只在 `queue.Empty` 分支检查，否则持续来消息可能使 15 秒上限失效。`put_nowait` 不等待可用空位，但不是硬实时或“完全不获取内部锁”的保证；减少事件量与保持回调短仍然必要。

队列保证传递 item 的线程安全，不会自动保证业务状态正确，也不会替你同步“模式、已消费按键和取消状态”。本课先完成单轮实验，Day05 再学习短锁区与跨轮状态；如果目前发现并发问题，先记录并补齐，不能带着未解释的竞态接入关窗。[Python：queue](https://docs.python.org/zh-cn/3/library/queue.html)、[Event](https://docs.python.org/zh-cn/3/library/threading.html#event-objects)、[单调时钟](https://docs.python.org/zh-cn/3/library/time.html#time.monotonic)

### 可选局部示例：传入回调与传递数据

你已有函数与参数基础，本课不把 `def` 当入门作业。新重点是把函数交给事件库、由库决定何时调用，以及将数据从回调传出；下面用短例子确认这个机制，熟悉部分可快速略过。

```python
import queue

def announce(item):
    print("收到：", item)

def deliver(value, handler):
    handler(value)

mailbox = queue.Queue()
mailbox.put_nowait("蓝色卡片")
deliver(mailbox.get_nowait(), handler=announce)
```

预期输出 `收到： 蓝色卡片`。

逐步解释：`def` 定义函数但不立刻执行函数体；队列保存字符串；`get_nowait()` 取出刚放入的数据；`handler=announce` 把函数对象传进去；`handler(value)` 才真正调用它。`get_nowait()` 不等待，队列空时抛 `queue.Empty`；本例先放后取，所以没有触发。

修改练习：更换卡片文字，并在 `announce` 中加一个前缀；解释为什么应传 `handler=announce`，而不是预先执行 `announce(...)` 后把返回值当回调。这个例子没有启动线程，也没有拦截输入，不可据此认为已验证线程行为。

本课主线程可用 `try / except queue.Empty` 处理正常超时，沿用 Day03 异常语法；用 `finally` 安排 listener 的停止和收尾。不将所有异常当作正常超时，不吞掉 Windows filter 的内部拦截异常。

### 自己动手与本任务验收

1. 自己决定事件记录如何表达，把鼠标事件的必要值复制后传出；键盘仅处理取消需要的信息，不记录普通输入。
2. 主线程接收并显示必要信息，区分正常 `queue.Empty` 超时和真实异常；窗口查询留在回调外。
3. 用 `time.monotonic()` 的差值检查本轮期限；有事件、无事件两条路径都检查。按第 1 节运行同一个文件，先验证无输入也能结束。

工程产出是必要事件与到期退出的原始结果；学习产出是“事件来自何处→数据怎样复制→主线程怎样收到→谁负责收尾”的解释。队列与 Event 不会自动建立完整业务状态，尚未拦截时不能把通知成功记作目标没收到输入。

## 4. 任务三（B 阶段）：选择性拦截一次点选或取消，只识别

### 必要原理：传播、消费与按下/松开配对

**选择性拦截**：本课用 Windows 专用 `win32_event_filter` 判断当前输入是否应该继续传播；需要阻止时，在对应 listener 上调用 `suppress_event()`。`suppress=True` 会全局抑制该监听器范围的所有输入，不适合作为本项目“仅模式内消费选择与取消”的默认设置。[pynput：选择性拦截](https://pynput.readthedocs.io/en/latest/faq.html#how-do-i-suppress-specific-events-only)

以下返回值千万不要混为一谈：

| 所在位置 | 动作 | 实际含义 |
|---|---|---|
| 普通 `on_click` / `on_press` 等回调 | 返回 `False` | 停止该 listener，不等于把原输入拦住 |
| `win32_event_filter` | 返回 `False` | 不再交给该 listener 的后续普通回调，不能据此认为目标收不到输入 |
| `win32_event_filter` | 调用该 listener 的 `suppress_event()` | 在 Windows 后端阻止当前输入事件传播 |

本课 B 阶段选择低层 filter 作为输入入口，避免同一个动作在 filter 和普通回调各处理一次。被拦的事件不能指望随后还触发普通回调。维护者实现中的 `suppress_event()` 通过专用异常结束当前分发；需要保留的数据应先复制并入队，不在它后面安排必须执行的操作，也不捕获所有异常将它吞掉。[Windows 后端实现](https://github.com/moses-palmer/pynput/blob/master/lib/pynput/_util/win32.py)

**成对输入与退出时机**：若消费了某次左键/右键按下，应记住它对应的松开也要消费；Esc 同理，还需考虑按住时的重复按下。取消业务上的选择，不等于立即卸载钩子。否则残留松开可能到达目标，出现菜单或不一致输入。仅剩“松开收尾”时不再接受第二个选择；完成配对后才恢复空闲并允许下一轮。

若按下发生在模式外、松开发生在模式内，也不能只凭当前模式把这次松开当成一次新选择。测试先在没有按住键或鼠标时进入模式，跨边界情形列为后续状态测试，未测不写通过。

Windows 上回调可能运行在系统输入相关线程中，长时间等待会影响其他应用输入；回调不执行 `sleep`、`input`、网络、长时间文件操作或窗口信息查询。先复制必要数据并迅速返回，把识别和显示交给回调外处理。[pynput：回调线程](https://pynput.readthedocs.io/en/latest/mouse.html#the-mouse-listener-thread)

### 本任务所需函数：Windows filters

导入：`from pynput import mouse, keyboard`。以下变量名表示你自己定义的对象或函数，不是完整程序。

| 调用形式 | 参数、返回与边界 | 本任务用途与时机 |
|---|---|---|
| `mouse.Listener(win32_event_filter=mouse_filter, suppress=False)` | filter 形如 `def mouse_filter(msg, data):`；返回 listener | B 阶段选择性消费鼠标输入；替换 A 阶段入口，不叠加两套相同选择处理 |
| `keyboard.Listener(win32_event_filter=key_filter, suppress=False)` | filter 也接收 `(msg, data)`，但结构是键盘结构 | B 阶段只对模式内 Esc 及其配对收尾作取消处理 |
| `listener.suppress_event()` | 无参数，消费当前 filter 正在处理的事件；会中断当前分发 | 只能在对应 Windows 输入 filter 内使用，不是事后从主线程补调用 |

### filter 参数、消息常量与数据有效期

`msg` 是消息种类，不是鼠标按键对象。导入 `win32con` 使用命名常量，不把下面的编号当作可调参数：

| 常量 | 含义与值 |
|---|---|
| `win32con.WM_LBUTTONDOWN` / `WM_LBUTTONUP` | 左键按下/松开，`0x0201` / `0x0202` |
| `win32con.WM_RBUTTONDOWN` / `WM_RBUTTONUP` | 右键按下/松开，`0x0204` / `0x0205` |
| `win32con.WM_KEYDOWN` / `WM_KEYUP` | 普通键按下/松开，`0x0100` / `0x0101` |
| `win32con.WM_SYSKEYDOWN` / `WM_SYSKEYUP` | 系统键消息，例如有 Alt 参与的情形，`0x0104` / `0x0105`；也要识别类别，不能把所有键都当 Esc |
| `win32con.VK_ESCAPE` | Esc 虚拟键码，`0x1B` / `27`，无时间单位；用于比较键盘 `data.vkCode` |

鼠标 `data` 是 Windows `MSLLHOOKSTRUCT`：通过 `data.pt.x`、`data.pt.y` 读取该事件的屏幕点。键盘 `data` 是 `KBDLLHOOKSTRUCT`，用 `data.vkCode` 判断是否 Esc；它没有鼠标的 `pt` 字段。不要在处理队列时重新 `GetCursorPos()` 替代点击坐标，鼠标可能早已移动。

不要把原始 `data` 对象或指针存到队列稍后使用；回调有效期之外不能依赖其底层内存。取出必要的 Python 整数、字符串或元组作为自己的事件记录。鼠标移动事件频繁，本课不入队每一帧移动、不记录所有按键，只处理任务需要的选择、取消和配对信息。

坐标约定要验证：监听坐标与查询函数在混合 DPI/多屏环境可能存在坐标空间差异。先在同一主屏、同一环境用已知窗口对照；不自行乘缩放倍数。坐标对不上时不进入关窗整合，保留布局、缩放和点位证据。

依据：[鼠标结构](https://learn.microsoft.com/en-us/windows/win32/api/winuser/ns-winuser-msllhookstruct)、[键盘结构](https://learn.microsoft.com/en-us/windows/win32/api/winuser/ns-winuser-kbdllhookstruct)、[虚拟键码](https://learn.microsoft.com/en-us/windows/win32/inputdev/virtual-key-codes)、[pynput 鼠标 Windows 后端](https://github.com/moses-palmer/pynput/blob/master/lib/pynput/mouse/_win32.py)。

### 同时复用的通信与收尾函数

`events.put_nowait(item)` 传自己的 Python 数据；主线程 `events.get(timeout=0.1)` 取得事件，超时为 `queue.Empty`。若使用 `threading.Event()`，`set()` / `clear()` 改单一标志，`is_set()` 读取它；它们不自动完成状态转换。监听启动仍用 `start()` / `wait()`；完成配对后 `stop()`，主线程 `join(timeout=1.0)` 并用 `is_alive()` 核对退出。时间参数单位都是秒，具体职责分别见任务一、二，不能在 filter 内阻塞等待。

### 自己动手与本任务验收

改用 Windows filters 做选择性拦截。主线程用终端确认或你自己设计的明确操作请求进入模式；初始化、等待 listener 就绪时还不接受选择。完整组织由你设计，目标是以下行为：

- 模式外普通点击、右键、Esc 均保持原行为。
- 模式内左键只接受一个选择，用该事件坐标做 Day02 查询；输出目标信息，绝不执行 Day03 请求。
- 模式内右键/Esc 表达取消，不识别为关闭目标；相应输入及配对松开被消费，其他键不全局封锁。
- 输入 filter 内只作必要的短判断、复制、状态标记与通知；窗口查询、输出及等待由外部主线程处理。
- 选择或取消后先停止接纳新选择，完成已消费输入的配对收尾，再恢复空闲；不在按下刚到达时立即停止 listener。
- 达到实验上限或出现异常时能退出并清理两个 listener；把退出原因与未完成配对的异常恢复情况写进记录。

本课先要求一轮可靠，不要求已经在同进程中重复进入多次；反复运行脚本不是 Day05 的连续三轮测试。卡在 B 阶段可继续保留 A 阶段可工作的版本，记录 B 尚未通过，不因到点降低“不透传”的标准。

运行自己的 `lessons/day04_pick_only.py`，用第 6 节场景同时观察程序通知与目标反应。工程上选择与两种取消均不透传、无关闭请求；学习上说清普通回调返回、filter 返回和 `suppress_event()` 的区别。没有目标侧观察就不记拦截通过。

## 5. 任务四：核对退出、配对收尾与输入恢复

**本任务所需函数与机制**：`listener.stop()` 无参请求停止；主线程 `listener.join(timeout=1.0)` 等待退出，返回 `None` 不能证明结束，须再用无参 `listener.is_alive()` 返回的布尔值核对。两个 listener 分别收尾，停止的实例不能重启。`time.monotonic()` 的秒数差用于总期限；`finally` 安排普通退出与异常收尾，不保证强杀时执行。正常停止前仍需消费已拦按下对应的松开，不能拿 `stop()` 替代配对。

### 自己动手与验收

在同一个 `lessons/day04_pick_only.py` 中，分别验证选择、右键取消、Esc 取消、无人操作到期和 Ctrl+C 回退后的输入与 listener 状态。运行仍用第 1 节命令；只测到正常路径就明确异常恢复待补。最小目标是能说明谁停止哪个资源、何时允许恢复，完整场景表在第 6 节。

### 卡住时的分层提示

分层提示：

1. 是“没有通知”“有通知但目标也响应”“取消后仍有动作”，还是“退出后输入异常”？先选一个现象。
2. 有通知但没拦住，核对使用的是普通回调返回、filter 返回，还是 `suppress_event()`；三者语义不同。
3. 拦住后主线程收不到数据，检查是否把入队放到了会中断分发的调用之后，或依赖了不会到达的普通回调。
4. 右键菜单残留、Esc 影响目标或鼠标状态异常，分别检查按下/松开的消费记录与停止时机；不要用固定 sleep 猜松开已经发生。
5. 识别偏移，保留事件的原始点与屏幕环境，检查是否事后又读了光标或混用了坐标空间。

## 7. 排错顺序

顺序：环境与版本 → A 阶段启动/收尾 → 回调签名 → filter 语义 → 事件配对 → 队列与外部处理 → 坐标与模式边界。

| 现象 | 检查方向 |
|---|---|
| 启动后马上结束 | 主线程是否保持运行；是否只 start 就到了文件末尾 |
| `... is not callable` | 是否把调用结果当成回调传入，或变量覆盖了函数 |
| 回调报参数数量错误 | 区分普通回调和低层 filter；核对安装版本与完整报错，不随意删参数 |
| 打印“取消”，目标仍弹菜单 | 只停止监听或只过滤普通回调；也可能漏了松开 |
| 拦截后没有后续通知 | 数据复制/入队是否在 `suppress_event()` 之前；普通回调可能不会再到达 |
| 输入卡顿 | 回调是否 print、sleep、input 或执行窗口查询；高频移动是否塞满队列 |
| 停止后再次启动报错 | 同一 listener 不能重启；新实例或常驻方案需由你明确设计 |
| 点位与目标不一致 | 是否使用后来鼠标位置、跨显示器坐标是否验证；先回只识别实验 |
| 一个 listener 结束另一个仍在 | 两个生命周期需分别收尾；主线程检查存活与异常 |
| 终端退出没有显示回调异常 | 在主线程 join 核对；不能把无输出当无异常 |

## 8. 技术面试与参考答案

题目与对应参考答案放在一起，可自主阅读、复述或按需分次复习，无需逐题回复。看过答案与能独立解释分别记录。

### 模块 A：事件驱动与 listener 生命周期（3 题）

#### A1. 把函数对象传给 listener 与在构造时调用该函数有什么区别？为什么回调不能假定运行在主线程或 GUI 线程？

**参考答案**：传函数对象是注册未来由库发起的调用，构造时写调用括号则先执行并把返回值交给库，可能传入 `None`。事件参数由库按回调契约提供。pynput 的线程/平台后端负责分发，Windows 输入回调不能假定具有 GUI 主线程身份；本项目只在回调做短处理，再通知业务，未来由 Qt 合适的线程更新控件。易错点是认为“这个函数定义在主文件”就会在主线程执行。

#### A2. `start`、`wait`、`stop`、`join` 分别解决什么问题？为什么 `join(timeout=1)` 返回不能证明 listener 已结束，停止的实例也不能直接重新启动？

**参考答案**：`start` 发起后台运行，`wait` 等库报告 ready，均不证明实际拦截效果；`stop` 请求停止；`join` 等退出，并可暴露回调异常。带超时 join 返回值是 `None`，需用 `is_alive` 核对；不能从线程里 join 自己。实例基于线程，停止后不能重新 start。两种重复使用策略是新建 listener，或常驻监听并切换业务标志；要同时安排两个 listener 的收尾，不能只停鼠标就认定键盘也停了。[listener 说明](https://pynput.readthedocs.io/en/latest/mouse.html)

#### A3. 为什么原型先用 pynput，而不是循环读取鼠标或只监听 Qt 按钮事件？对平台、GUI 和最终打包分别有什么影响？

**参考答案**：当前需要应用外真实点击及选择性消费，pynput 减少原生钩子绑定工作；轮询主要观察状态，可能漏短动作且不能替代传播控制，Qt 自己的控件事件则不自动覆盖外部窗口。代价是 Windows 后端相关能力、版本兼容与生命周期验证。接 GUI 时不能在 GUI 线程永久 join；构建时要检查动态后端是否被收集，源码可运行不保证打包可运行。没有做性能对照，不能声称它一定比原生实现快。

### 模块 B：输入传播、坐标与成对事件（4 题）

#### B1. 普通回调返回 `False`、Windows filter 返回 `False`、调用 `suppress_event()` 有什么不同？为什么打印“选中了”仍可能触发目标按钮？

**参考答案**：普通回调 `False` 用于停止 listener；filter 的 `False` 用于隐藏后续普通回调；消费当前系统输入要在对应 Windows filter 内调用 `suppress_event()`。如果只监听并输出，目标仍可收到原点击，所以终端成功文字不是不透传证据。本项目用可观察插入点/选区或菜单的普通测试窗口，同时核对程序事件与目标反应；不采用无差别全局抑制。[选择性拦截契约](https://pynput.readthedocs.io/en/latest/faq.html#how-do-i-suppress-specific-events-only)

#### B2. 鼠标按下时取消模式并立即停止 listener，可能留下什么问题？按下在模式外、松开在模式内时又该注意什么？

**参考答案**：一次动作通常有按下/松开，立即卸载可能只吃掉按下，松开落到目标；按住 Esc 还会重复按下。业务取消应停止接纳新选择，但保留必要配对收尾，完成后才正常退出。反过来，模式外已透传的按下不能在模式内只凭松开制造一个新选择。易错点是一个布尔“空闲”既表示业务结束又表示所有输入已清理。实际配对记录和转换由用户设计，以按住再放开、边界切换实验验证。

#### B3. 为什么把原始 `data` 保存到队列，稍后再读 `data.pt`，或消费时重新读取光标，都可能识别错目标？DPI 问题怎样验证？

**参考答案**：原始 `data` 关联系统回调内存，其有效期不由队列延长；应在回调内复制必要数值作为自己的数据。消费时重读光标拿到的是处理时刻，用户可能已经移开，不能代表点击点。先在同一显示器/缩放环境对照已知窗口，再记录混合 DPI、多屏布局与原始坐标；不同坐标空间不能凭缩放百分比随意换算。队列记录应能追溯当次事件，而不是引用后来变化的数据。[鼠标回调与 DPI](https://pynput.readthedocs.io/en/latest/mouse.html)

#### B4. 某 filter 调用了 `suppress_event()` 后才安排入队，主线程一直收不到选择。解释原因与定位方法；为什么不能用捕获所有异常来“让后面继续执行”？

**参考答案**：该后端通过专用异常中止当前分发，后面代码可能不会执行，也不能假定普通回调随后补上。先检查控制流和必要数据入队位置，按安装版本核对维护者实现，并保留主线程能看到的回调错误。把全部异常吞掉可能破坏拦截本身或掩盖真实错误；正确思路是在拦截前完成必要短操作，不靠强行继续执行。主线程不能事后补一次 suppress 来撤销已经传播的输入。[Windows 后端](https://github.com/moses-palmer/pynput/blob/master/lib/pynput/_util/win32.py)

### 模块 C：线程通信、响应与恢复（3 题）

#### C1. 队列、Event、业务状态各负责什么？队列线程安全为什么不保证只能选择一次？未来怎样保持 GUI 响应？

**参考答案**：队列传递事件，Event 通知一个条件，业务状态约束当前允许什么；三个角色不能互相替代。多个输入仍可能先后或交错通过“还在等待”的判断，需要单一决策责任或受保护的短状态转换，Day05 再整合验证。未来 GUI 通过有界处理或合适的跨线程通知接收结果，不直接搬入终端阻塞循环，也不从回调操作控件。易错点是把 FIFO 当成完整状态机或取消优先规则。

#### C2. 在输入回调中打印大量日志、等待用户输入或查询窗口有什么风险？只把 `put` 换成 `put_nowait` 是否足够解决延迟和内存增长？

**参考答案**：Windows 输入相关回调里慢操作可能延迟其他应用输入；大量移动日志还会增加 CPU、I/O、队列积压。`put_nowait` 只是不等待队列空位，不承诺无内部锁或硬实时；默认无限队列仍可能增长。项目只复制所需选择/取消/配对事件，主线程处理识别与适量输出；若设置容量，还要设计溢出恢复，不能丢失松开等必要事件后假装正常。不靠提高线程数量掩盖阻塞。

#### C3. `0.1`、`15`、`1.0` 秒和 `VK_ESCAPE=27` 各是什么约定？若仅在队列空时检查超时会怎样，如何验证正常恢复与异常恢复？

**参考答案**：`0.1` 是主线程等待队列的秒数，`15` 是教学实验总上限，`1.0` 是线程退出等待检查窗口，均属可调整工程选择；`27` 是 Esc 虚拟键码，无时间单位，不能当延迟。期限用单调时钟差值判断，有事件也要检查，否则消息持续到来可能永不超时。手测无输入到期、选择/取消后恢复及 listener 存活状态；强制终止是异常回退，不能证明配对收尾成功。软件后续还需 GUI、光标和发布回归，而不是只验证终端能退出。
