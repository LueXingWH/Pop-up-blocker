## 2. 任务一（A 阶段）：采集事实，只打印过滤判定与理由

**必须独立编写的核心**：过滤判定、状态设计、事件接纳、取消与输入配对、错误恢复、各组件及未来 GUI 的核心接线。**AI 可辅助的非核心**：本次规范/教程、接口核对、审查、测试记录和 UI 文案建议；后续布局、资源、辅助构建文档等按明确授权处理，不能顺便代写业务模块或通信执行链。

### 先查事实，再给可解释的判定

句柄非零，只说明有一个候选引用；顶层、可见、有标题也不能单独证明它是允许处理的普通窗口。本课把“采集到哪些事实”和“依据哪些规则允许或拒绝”分开表达，让一次判定能追溯到数据。

至少需要辨认这些拒绝情形：

| 拒绝情形 | 依据与边界 |
|---|---|
| 空句柄、句柄不存在或信息查询失败 | 没有可靠候选；本轮不给关闭请求，不用上轮信息补齐 |
| 本程序自己的窗口 | 候选窗口创建者 PID 与 `os.getpid()` 比较；按进程身份而非标题比较 |
| 桌面、桌面外壳、任务栏 | 桌面句柄与实际采集到的外壳窗口信息一起判断；不能只排除一个桌面句柄 |
| 不在本次支持范围的窗口 | 暂不确定的弹出层、特殊窗口、映射不明目标只记录与拒绝，不猜测应用身份 |
| 已取消、本轮已接纳选择或旧轮事件 | 这是业务状态问题；即便句柄是普通窗口也不能再次执行 |

`GetDesktopWindow()` 返回的桌面窗口，与鼠标落在桌面图标、壁纸或任务栏上命中的对象未必是同一窗口。常见 Windows 外壳类名有 `Progman`、`WorkerW`、`Shell_TrayWnd`、`Shell_SecondaryTrayWnd`；它们是应在当前机器验证的实现特征，不是 Windows 承诺永远不变的完整名单。用 Day02 只读实验采集直接命中与根窗口的类名和 PID；信息不完整时不要向该对象发送消息。参考真实项目的[任务栏类名定义](https://github.com/TranslucentTB/TranslucentTB/blob/develop/Common/constants.hpp)及[桌面外壳层级变动记录](https://github.com/lively-community/lively/issues/2074)，这些项目观察不等于官方兼容性承诺。

禁止根据“类名不在这几个里面”就声称已证明任意窗口都可以关闭，也不能把空标题等同桌面。今天真实请求先限定为你当次明确核对的普通测试窗口；扩大支持范围时新增手测记录。这是实验范围约束，不是最终所有普通窗口都已支持的声明。

任务栏图标本身不是所代表应用窗口的句柄。今天点击任务栏应拒绝，不做“顺便猜一个关联窗口”的映射；映射属于核心稳定后的可选扩展。

### 过滤信息有哪些局限

`IsWindowVisible` 反映窗口可见样式，不保证肉眼看得见：被覆盖的窗口也可能返回真。因此它只是信息或必要条件之一，不能充当“普通窗口认证”。

PID 是进程标识，HWND 是窗口标识，同一 PID 可以拥有多个窗口。当前 Python 脚本的终端窗口通常由终端/控制台宿主进程创建；它的 PID 未必等于脚本 PID。因此用终端做“自己窗口”测试不能随意认定失败或通过。等 Day06 建立 PySide6 窗口后，再点自己的主窗口验证；目前可以核对规则的判断逻辑，但实机验收标待完成。

句柄和 PID 也有生命周期，可能复用；采集后不长期保存成永久允许名单。确认后的目标若改变或查询失败，本轮放弃。靠几次检查不能消除所有跨进程竞态，要保留投递错误与限制。[Microsoft：IsWindow 的时序边界](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-iswindow)

### 本任务所需函数、返回值与错误

导入形式：`import os`、`import win32process`、`import win32gui`。`win32process` 也来自 pywin32，不是需要额外 pip 安装的包。

| 调用形式 | 输入与返回 | 时机和用途 |
|---|---|---|
| `os.getpid()` | 无参数；返回当前 Python 进程的整数 PID，无时间单位 | 确定“自己是谁”；不需要传窗口，因为查的就是调用进程 |
| `win32process.GetWindowThreadProcessId(hwnd)` | 一个窗口句柄；返回 `(thread_id, process_id)` 两个整数 | 查询候选窗口由哪个线程/进程创建。第一个不是 PID，不把整个元组与自己的 PID 比较 |
| `win32gui.GetDesktopWindow()` | 无参数；返回桌面窗口句柄 | 获取桌面基线；不覆盖所有外壳窗口 |
| `win32gui.IsWindowVisible(hwnd)` | 一个窗口句柄；返回非零/零 | 观察可见样式，不保证未被遮挡，不独立作为允许依据 |
| `win32gui.IsWindow(hwnd)` | 一个句柄；返回非零/零 | 观察此刻是否存在；仍需处理后续查询或投递失败 |
| `win32gui.GetClassName(hwnd)` / `GetWindowText(hwnd)` | 一个句柄；各返回类名/文字字符串 | 与当次命中与根对象对应记录；空标题不是桌面证明 |

`GetWindowThreadProcessId` 的 Python 返回值已包含 PID；微软 C 文档中指针输出参数由包装处理，本课不用自己创建 C 指针。异常仍按 Day03 用 `pywintypes.error` 保留原始原因。

依据：[pywin32 线程/PID](https://mhammond.github.io/pywin32/win32process__GetWindowThreadProcessId_meth.html)、[可见样式](https://mhammond.github.io/pywin32/win32gui__IsWindowVisible_meth.html)、[窗口类名](https://mhammond.github.io/pywin32/win32gui__GetClassName_meth.html)、[Microsoft 桌面窗口](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getdesktopwindow)、[Python 当前 PID](https://docs.python.org/zh-cn/3/library/os.html#os.getpid)。

## 3. 任务二：自己设计本轮状态、唯一决定与同步边界

### 必要原理：状态、轮次与取消的有效时点

状态记录“当前允许哪些操作”。显示“等待选择”却仍接受两次点击，说明实际控制没有跟上文字。你要自己列出各状态与转换，不要求照搬导师给出的命名。

设计至少回答：什么时候允许开始；什么时候只接纳一个选择；拒绝目标后本轮怎样结束；什么时候允许再次开始；取消与请求执行交错时谁先被接纳；已消费输入何时完成松开收尾。**本课约定被拒绝的一次选择也结束本轮，显示理由后可重新开始。** 不静默留在模式中继续等下一次点击。

从“等待选择”到“本轮已经接纳一个决定”，需要避免两次事件都通过同一个旧条件。GIL 不是多步骤业务操作的原子性保证；队列也只保证消息传递，不自动维护业务状态。可让一个地方负责决策，并对仍由回调共享的少量状态使用短锁区；具体组织由你设计。[Python：Lock](https://docs.python.org/zh-cn/3/library/threading.html#lock-objects)

“业务已结束”和“输入配对已收尾”有时间差。Day04 消费的按下，其松开仍须处理；这段时间不能新接纳一轮。若正常退出、异常退出只各复位一半，下轮常会出现无法开始、重复执行或输入残留。

队列里的旧事件不会因你把模式变量设回空闲而消失。你可以为事件记录轮次，或采用其他能说明正确性的办法；要能说明如何防止上轮事件被下轮误用。轮次编号是自己的业务标识，没有 Windows 特殊含义，也不要求从某个特定数字开始。

取消只能阻止尚未决定执行的本轮动作，不能撤销已经投递的 `WM_CLOSE`。选择和 Esc 几乎同时发生时，要有一致、可记录的接纳顺序；一轮一旦进入执行决定，不再把后来的取消文字伪装成“请求已被撤销”。状态互斥不能等到日志打印后才建立。

### 本任务所需函数与同步工具

`threading.Lock()` 无参数创建锁对象。`with lock:` 进入时获取锁，退出时释放锁；其他线程不能同时持有同一把锁。它保护你明确放进该区域的共享状态，不会自动保护所有变量，更不会锁住另一个应用的窗口。

在锁内只读写少量本地状态；不做窗口查询、投递、`input`、`sleep`、`join` 或长时间输出。输入回调也可能受争锁影响，因此锁区要短、无等待工作，不能以加锁为理由让输入线程长期等待。不要持有锁等待另一个必须拿锁才能完成的线程。

`with` 是上下文管理语法，不只用于锁：进入/退出行为由对象协议定义。这里锁帮助一次受保护的检查与更新保持一致；不要求你今天写自己的上下文管理类。`finally` 用于各条退出路径的收尾，但不能保证强制结束进程时执行，也不能拿它替代 Day04 的按键松开配对。

本任务还复用 `queue.Queue()` 创建事件队列，`put_nowait(item)` 传递复制后的 Python 数据，`get(timeout=0.1)` 取得并移除事件，超时为 `queue.Empty`；如用 `threading.Event()`，`set()` / `clear()` 设单一标志，`is_set()` 读取布尔状态。这些来自标准库 `queue`、`threading`，不能替代本轮唯一决定与旧事件失效规则。时间参数单位为秒；窗口查询和投递不放进状态短锁区。

### 先运行注释示例：短锁区与会话快照

```python
import threading

# 只演示本地状态快照，不监听输入、不查询窗口、不执行关闭。
lock = threading.Lock()  # 标准库锁；无参构造。
state = {"session_id": 1, "mode": "normal"}

with lock:
    # 检查/复制放短锁区；查询窗口、打印和等待留在锁外。
    snapshot = state.copy()

with lock:
    # 模拟之后切换了配置；不是允许产品在会话中途切换策略。
    state["mode"] = "force"

print("当时复制的值：", snapshot["mode"])
print("后来配置的值：", state["mode"])
```

预期依次输出 `当时复制的值： normal` 与 `后来配置的值： force`。将此独立示例保存为自己的临时实验，用项目解释器运行即可。这里 `copy()` 是浅复制，当前值只有整数和字符串；以后放入嵌套可变对象时不能据此认定所有内容都被冻结。锁保护参与同一协议的本地访问，不锁定外部窗口；本例没有制造并发竞争，不能证明产品无竞态。

短改写任务：自己把后来配置的 `session_id` 改为 2，打印快照与当前标识，解释旧事件为什么仍应携带原标识。再结合 Day4 的真实队列记录设计接纳/丢弃实验；不能只凭“使用了 copy 或 Lock”就声称旧事件已处理、会话策略已固定。运行方法是 `项目解释器.exe 你的实验文件.py`，不需要安装 threading。

## 5. 任务四：验证各条结束路径、输入恢复与同进程三轮

**本任务所需函数与参数**：两个 listener 分别调用无参 `stop()` 请求停止，在主线程 `join(timeout=1.0)` 后用无参 `is_alive()` 的布尔值核对；`join` 返回 `None` 不等于退出成功，停止的实例不能重启。按下/松开配对仍由输入层负责，业务结束不立即取消这项责任。共享状态如使用 `threading.Lock()`，只在 `with lock:` 内保护短检查/更新；`finally` 收尾不能替代输入配对或保证强杀时执行。

## 7. 常见问题与定位顺序

顺序：单个能力是否已独立验证 → 当次候选事实 → 判定理由 → 本轮接纳时机 → 请求次数 → 输入配对与退出 → 下一轮残留。

| 现象 | 优先检查 |
|---|---|
| 自己 PID 比较永远不对 | 是否把 `(thread_id, process_id)` 整体或第一项当 PID；是否把宿主终端当 Python 自己的 GUI |
| 过滤桌面却漏图标/任务栏 | 是否只比较 `GetDesktopWindow()`，没有采集命中与根对象的外壳信息 |
| 所有空标题都被视为桌面 | 标题不等于类型；回到已采集的句柄、类名和身份 |
| 可见窗口却在别的窗口后面 | `IsWindowVisible` 检查样式，不检查遮挡 |
| 一击两个请求 | 按下/松开重复，或同一输入在多个入口处理，或接纳条件未互斥 |
| 取消后下一轮自己执行了 | 是否有旧队列事件，轮次与状态是否对应 |
| 显示空闲但不能再开始 | 两个 listener 生命周期、输入配对、业务状态是否分别复位 |
| 接入终端确认后 Esc 不响应 | 主线程是否阻塞在 `input()`；取消不能只排在无人处理的队列里 |
| 加锁后输入卡住 | 是否锁内做查询、打印或等待另一个线程；先缩短锁区并保留复现 |
| 目标未关闭却显示成功关闭 | 把投递结果写成实际关闭结果；检查状态文案与证据 |

### 模块 A：身份、过滤依据与边界（3 题）

#### A1. HWND、线程 ID、PID 与标题分别标识什么？分析 `GetWindowThreadProcessId` 的返回顺序，为什么终端不能随意冒充自身 GUI 窗口来验收？

**参考答案**：HWND 引用窗口，线程 ID/PID 分别标识创建线程与进程，标题是可变属性。包装返回 `(thread_id, process_id)`，第二项才与 `os.getpid()` 比较；同一进程可有多个窗口。终端通常由终端/控制台宿主创建，PID 未必属于脚本。规则逻辑可先检查，但应在 PySide6 自身窗口出现后实点验证，不能拿“终端 PID 不同”证明规则错或自身过滤已通过。易错点是将窗口、进程和显示文字混为唯一身份。

#### A2. 为什么只排除 `GetDesktopWindow()`、只看空标题或只检查可见样式都不足以过滤？固定外壳类名有什么价值和限制？

**参考答案**：桌面基线句柄不覆盖全部壁纸/图标/任务栏对象；空标题既可能是普通窗口也可能是控件；可见样式不保证不被遮挡。外壳类名有助于识别当前环境已知对象，但不是完整且永久的 API 保证。项目采集命中与根对象的数据，记录拒绝理由；未知类型在实验范围外不执行。易错点是把“没命中几个拒绝类名”推成“已证明一定可关闭”。

#### A3. 你已检查句柄、PID 和类名，目标在投递前变化了怎么办？为什么一份历史允许名单不能成为长期安全证明？

**参考答案**：信息查询与使用间存在竞态，窗口和进程标识均有生命周期；目标改变、信息不全或调用失败应放弃当前动作并保留原因。缩短间隔与重核对降低风险，不能锁住别的程序或承诺绝不复用。历史名单至多是某次实验记录，不能让重建对象自动获准。追问“锁住本程序能否锁住目标”：不能，本地锁只约束参与同一同步协议的代码。[IsWindow 边界](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-iswindow)

### 模块 B：状态、同步与输入恢复（4 题）

#### B1. 界面状态文字、业务模式、listener 运行状态和输入配对状态有什么区别？为何一次被拒绝的选择也要明确结束本轮？

**参考答案**：文字是展示，模式约束允许动作，listener 状态表示资源是否运行，配对状态表示哪些已消费输入还欠松开。业务结束可先于配对收尾，只有相关资源和事件都满足条件才再次开始。本课拒绝也结束本轮，使用户收到明确反馈并可重新开始；不能只打印理由却留下不清楚的等待模式。易错点是在任意结束分支直接设一个“空闲”就认为所有清理已完成。

#### B2. 两个来源几乎同时看到“正在等待”，队列又是线程安全的，为什么仍可能重复执行？GIL、Lock、单一决策者各能解决什么、不能解决什么？

**参考答案**：两个操作可能先后读到同一旧状态，再各自更新/执行；队列只保护入出队，不保护这组业务检查。GIL 不保证多步骤决策原子性，也不应作为应用同步设计。Lock 可保护参与者共享的短检查/更新；单一决策者可减少共享写入，但仍需与实时拦截及资源收尾配合。窗口查询、投递、等待不放长锁区；本地锁也不消除目标窗口的外部竞态。易错点是“队列安全，所以业务只会执行一次”。

#### B3. 上一轮取消后队列里还有选择事件，下一轮刚开始就误发请求。根因是什么？如何说明轮次或其他隔离策略有效，而不是“清空队列就一定安全”？

**参考答案**：旧事件被按新一轮条件解释，缺少事件所属周期与有效性验证。可以记录轮次并由接纳方核对，也可采用其他明确生命周期隔离；关键是失效规则与重新开始边界可证明。清队列时生产者还可能继续入队，不能据一次清空断言无旧事件。验证要在同一运行中取消后立刻重进，保留事件所属轮次、接纳与丢弃理由，不只重启脚本。

#### B4. 选择与 Esc 很接近时，怎样定义可解释的先后关系？为什么“已取消”不能撤销投递出去的 `WM_CLOSE`，结束后又如何证明可以重进？

**参考答案**：明确哪个地方按何种顺序接纳本轮唯一决定，记录该时点与轮次；先被有效接纳的取消阻止尚未决定的执行，已决定/已投递不能靠后来一行取消文字撤销。系统没有因本项目设置空闲就收回队列里的关闭消息。测试同进程有效、取消、有效三轮，并补快速重复输入、异常和松开收尾；未出现重复只是有限场景证据，不能宣称覆盖所有调度顺序。

### 模块 C：模块化、审查与软件工程（3 题）

#### C1. 你的输入、识别、过滤、执行与界面之间应该交换什么？为什么拆成五个文件仍可能没有真正模块化？

**参考答案**：各层交换明确的数据与结果事实：输入时刻数据、候选与来源、允许/拒绝及理由、投递或异常、供 GUI 展示的状态。资源拥有者和最终决策责任要明确；不让低层直接操作控件，也不让过滤函数暗中投递请求。文件数量不是模块化：若相互修改全局变量、重复决策或共享不明 listener，拆文件仍有耦合。项目先说明输入输出、错误和生命周期契约，函数/文件命名与接线由用户实现。

#### C2. 审查一个“正常路径可用”的整合版本，应先检查哪些异常、资源、性能和不安全操作？发现问题后如何指导修复而非重写？

**参考答案**：先核实正确目标、一次请求、取消/拒绝/查询失败/投递失败是否都恢复；再查 listener/线程泄漏、成对输入、旧事件、GUI 线程越界、锁内慢调用与无关高频日志。警惕广播、空/旧句柄、强杀后备和虚报关闭成功。报告具体位置、触发条件、机制、修改方向与最小复现/回归方法，让用户修改后复测；不因一个问题重写整个程序，也不拿样式偏好盖过功能风险。

#### C3. 本课终端原型通过，距可安装的 Windows 软件还缺什么？解释器、依赖、独立运行构建、安装包、图标与版本信息有什么关系？

**参考答案**：还需 GUI 按钮与状态、事件循环响应、跨线程边界、光标反馈/恢复、自身过滤实测，再做依赖与资源收集、独立运行构建、版本记录和安装卸载验证。源码运行需要合适解释器与库；打包工具可以携带运行时，不等于所有代码都变成无解释器机器码。独立运行产物不自动具备安装/卸载能力；安装程序部署应用与图标等资源，卸载还要明确程序文件与用户数据的处理。易错点是“生成一个 exe 就交付完成”。今天只建立关联，后续按计划逐项教学和验收。
